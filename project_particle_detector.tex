\section{Introduction}

This project develops an object oriented C++ program to simulate a particle detector.
The detector was composed of sub-detectors, like the example of the \textcolor{red}{CMS} detector \cite{cms_detector} in Figure \ref{fig:CMS_schematic}.
Different particle types are passed through the detector, with the sub-detectors response depending on the physical properties of the particle.
\begin{figure}[H]
      \centering
      \includegraphics[alt={Put short description for screen readers here},width=0.9\textwidth,keepaspectratio=true]{report_assets/report_figures/CMS_schematic.png}
      \caption[Short caption for list of figures]{
      Schematic of the CMS detector \cite{cms_detector}. Sub-detectors of note are the: silicon tracker, muon chamber, ECAL and the HCAL.
      }
      \label{fig:CMS_schematic}
\end{figure}

The main aim of the project was to practice object oriented programming principles, building a clear and extensible class structure for both particles and detectors.
The program possesses separate class hierarchies for both particles and sub-detectors, with base classes' \texttt{Particle} and \texttt{SubDetector}, respectively. Inheritance and polymorphism simplify the code and reduce repetition for the derived objects.
\texttt{SubDetector} objects are owned via unique pointers by a large detector class, \texttt{DetectorSystem}, which acts as a container class.

This report describes the key choices made throughout the design process, first considering the decisions required to meet the minimum functionality to a high standard, before discussing the choices that enabled more advanced features.
The final sections discuss how the program is used in \texttt{main()}, using figures to demonstrate the functionality, and how it could be improved.

\section{Design process \& considerations}

As mentioned previously, the key design considerations are discussed in two parts: minimum functionality and advanced features. These are further divided around the three main components of the program: the \texttt{Particle} and \texttt{SubDetector} hierarchies and the \texttt{DetectorSystem} class.

\subsubsection{Particles}
\label{sec:min_func_Particles}
\begin{figure}[H]
      \centering
      \includegraphics[alt={Put short description for screen readers here},width=0.9\textwidth,keepaspectratio=true]{report_assets/report_figures/UML_Particle_1.png}
      \caption[Short caption for list of figures]{
      UML class diagram for the \texttt{Particle} hierarchy. \textcolor{red}{Needs to be improved. Especially friends???}
      }
      \label{fig:Particle_UML}
\end{figure}
\texttt{Particle} was created as a pure abstract base class from which the particles are derived, meeting requirement 1 of Table \ref{tab:min_func_summary}.
Figure \ref{fig:Particle_UML} shows the \texttt{Particle} base class data members, which were chosen because they represent intrinsic properties shared by all particles.
Figure \ref{fig:Particle_UML} also shows the composition relationship between \texttt{FourMomentum} and \texttt{Particle}, satisfying requirement 5 in Table \ref{tab:min_func_summary}.
This is implemented using a \texttt{std::unique\_ptr}, enforcing exclusive ownership of \texttt{four\_momentum}.
\texttt{FourMomentum} \texttt{components} remain stored by a raw pointer from Assignment 4.
The decision to implement dynamic memory meant that custom move/copy semantics were required.

Interaction logic was chosen to be stored in the \texttt{Particle} hierarchy rather than the \texttt{SubDetector} hierarchy.
This allowed for shared behaviour, such as charged particles interacting with the \texttt{Tracker} in Code snippet \ref{lst:interacts_with_tracker}, to be inherited by derived particles, reducing repetition and improving extensibility.
New particles can reuse existing logic where appropriate, while any particle specific interactions can be distinctly implemented.
This follows the open closed principle unlike if we chose to store in the \texttt{SubDetector} hierarchy, where every derived \texttt{SubDetector} would have to be updated if a new particle was created.
Detector specific conditions, such as \texttt{status}, remain within the \texttt{SubDetector} classes, separating whether interaction is physically possible from whether detection actually occurs, increasing flexibility and clarity.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{Particle} member function \texttt{interacts\_with\_tracker}. As seen in Figure \ref{fig:Particle_UML}, only \texttt{interacts\_with} member function defined in \texttt{Particle} and not overridden in the derived classes.},
    label={lst:interacts_with_tracker}
]
bool Particle::interacts_with_tracker() const
{
    if (charge_mag == 0)
    {
        return false; // Neutral Particles don't interact with Trackers.
    }
    else
    {
        return true; // Charged Particles interact with Trackers.
    }
}
\end{lstlisting}

As seen in Figure \ref{fig:Particle_UML}, the member functions, \texttt{interacts\_with}, were used instead of storing \texttt{SubDetector} names in a \texttt{vector} of \texttt{std::string} or \texttt{enum} data types.
This decision allows for the logic behind the interaction rule to be expressed where defined, as shown by Code snippet \ref{lst:interacts_with_tracker}, rather than stored only as a fixed result. 
Hence it also improves adaptability, since any future conditions such as energy thresholds can be added inside the relevant member function.
On top of this, it will be seen that the design choice greatly simplifies the detection, with \texttt{SubDetector} only having to call a single \texttt{bool} member function. 

The class hierarchy seen in Figure \ref{fig:Particle_UML} was decided upon based on shared properties of the particles required in Table \ref{tab:min_func_summary}.
\texttt{Photon} was derived directly from \texttt{Particle} due to it possessing distinct properties and not sharing behaviour with the other particles.
It became clear the inherited data members, \texttt{rest\_mass} and \texttt{is\_anti}, were redundant for \texttt{Photon} as it has no mass and is its own anti-particle. However, since they are not damaging and a necessity for most of the particles, it was worthwhile for them to remain as base data members.
To mitigate this the polymorphic \texttt{Photon::print\_info()} addresses the fact that photon's are their own anti-particle.
The same was done for the neutral \texttt{Pion}.


The charged leptons, \texttt{Electron} and \texttt{Muon}, were grouped under the intermediate base class \texttt{ChargedLepton} due to their shared properties and interaction behaviour, which can seen to be defined once in Figure \ref{fig:Particle_UML}.
Similar is done for the hadronic particles, where the common interaction logic is implemented in \texttt{Hadron} and consequently inherited by the derived objects.
A further intermediate base class, \texttt{Meson}, was introduced because mesons follow a general construction logic depending on the distinct data member \texttt{is\_charged}.
As shown in Code snippet \ref{lst:meson_construction}, this parameter controls if a charged or neutral \texttt{Meson} is instantiated, setting the appropriate \texttt{charged\_mag} and \texttt{rest\_mass}.
For charged mesons, \texttt{is\_anti} then determines the charge sign, while the polymorphic \texttt{print\_info} functions distinguish neutral particles that are their own anti-particles, such as \texttt{Pion}, from mesons with distinct anti-particles, such as \texttt{Kaon}.
This reduces repeated constructor and output  logic across derived \texttt{Meson} objects.
Baryons were not given an intermediate base class because their construction logic is not consistent, while the hierarchy still allows a baryon base class to be introduced later if more shared behaviour is added.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{Meson} parameterised constructor. Arguments \texttt{neutral\_rest\_mass} and \texttt{charged\_rest\_mass} are fixed by the derived \texttt{Particle}, \texttt{is\_charged} is chosen by the user and determines what type of \texttt{Meson} is constructed. The charge of the charged mesons is determined by \texttt{is\_anti}, with the anti-particle arbitrarily set as the negative particle.},
    label={lst:meson_construction}
]
Meson::Meson(double E, double px, double py, double pz, bool is_anti,
    bool is_charged, double neutral_rest_mass, double charged_rest_mass)

    : Hadron(E, px, py, pz, is_charged ? charged_rest_mass : neutral_rest_mass, is_anti, is_charged ? 1 : 0),
    is_charged(is_charged)
{
    if (Debug::show_messages)
    {
        std::cout << "Calling Meson Parameterised Constructor." << std::endl;
    }
}
\end{lstlisting}

\subsubsection{SubDetectors}
\label{sec:min_func_SubDetectors}

\begin{figure}[H]
      \centering
      \includegraphics[alt={Put short description for screen readers here},width=0.9\textwidth,keepaspectratio=true]{report_assets/report_figures/UML_DetectorSystem_SubDetector_2.png}
      \caption[Short caption for list of figures]{
      UML class diagram for the \texttt{SubDetector} hierarchy and its composition in \texttt{DetectorSystem}. \textcolor{red}{Needs to be improved.}
      }
      \label{fig:SubDetector_UML}
\end{figure}

The \texttt{SubDetector} hierarchy was initially developed using a pure abstract base class and one derived class, allowing the core interface to be tested before adding more derived classes.
Figure \ref{fig:SubDetector_UML} shows that base class has two data members \texttt{sd\_name} and \texttt{status}.
\texttt{sd\_name} simply distinguishes between \texttt{SubDetector} objects while \texttt{status} controls whether a \texttt{SubDetector} is active.
Since \texttt{SubDetector} manages no dynamically allocated data members, the default compiler copy/move operations are sufficient, so no custom copy/move semantics were required.
\textcolor{red}{How to mention status as advanced.}

To meet requirement 6 of Table \ref{tab:min_func_summary}, \texttt{Particle} objects must be passed through the derived \texttt{SubDetector}, which return the particle's energy.
This was implemented via a virtual base member function \texttt{detect}. As virtual it allowed each derived \texttt{SubDetector} to define its own detection response while sharing a common interface.
This common interface was utilised in \texttt{DetectorSystem} to pass a \texttt{Particle} through all contained \texttt{SubDetector} objects clearly and efficiently, as discussed later.

\begin{lstlisting}[
    style=vscode, 
    caption={
    Derived \texttt{MuonChamber::detect} definition acts as an example for how the \texttt{Particle} object's \texttt{interacts\_with} function is utilised in line 9.},
    label={lst:SubDetector_detect}
]
void MuonChamber::detect(Particle& particle) const
{
    // Check status of SubDetector.
    if (is_off())
    {
        return; // Exit function.
    }

    if (particle.interacts_with_muonchamber())
    {
        std::cout << "Muon Chamber (" << sd_name << ") measures the energy of the particle as: " << particle.get_four_momentum().get_E() << " MeV" << std::endl;
        // Will differentiate these later.
        std::cout << "The particle's true energy is: " << particle.get_four_momentum().get_E() << " MeV" << std::endl;
        std::cout << std::endl; // Line break.
    }
    else
    {
        std::cout << "Particle does not interact with the muon chamber (" << sd_name << "), no energy measurement." << std::endl;
        std::cout << std::endl; // Line break.
    }
}
\end{lstlisting}

Following the interaction design discussed in Section \ref{sec:min_func_Particles}, the \texttt{SubDetector::detect} uses the passed \texttt{Particle}'s relevant  \texttt{interacts\_with...} function to determine whether detection is physically possible.
Code snippet \ref{lst:SubDetector_detect}, line 9, demonstrates the simplicity of this approach.
The omission of \texttt{const} in the \texttt{particle} argument is discussed later in the advanced features section.

\subsubsection{DetectorSystems}
\label{sec:min_func_DetctorSystems}

\texttt{DetectorSystem} satisfies the final requirement of Table \ref{tab:min_func_summary}, by acting as a generic detector class that stores \texttt{SubDetector} objects.
As presented in Figure \ref{fig:SubDetector_UML}, the \texttt{sys\_name} data member differentiates \texttt{DetectorSystem} object's.
The other data member, as declared in Code snippet \ref{lst:container_pointer}, is a \texttt{vector} of unique pointers owning \texttt{SubDetector} objects.
This is what gives \texttt{DetectorSystem} its utility of being a container of multiple derived \texttt{SubDetector} objects polymorphically.
\begin{lstlisting}[
    style=vscode, 
    caption={Data member for \texttt{DetectorSystem} to manage the ownership of multiple \texttt{SubDetector} classes.},
    label={lst:container_pointer}
    ]
    private:
    std::vector<std::unique_ptr<SubDetector>> sub_detectors;
\end{lstlisting}
\texttt{std::unique\_ptr} was chosen over \texttt{std::shared\_ptr} because each \texttt{SubDetector} should belong to a single \texttt{DetectorSystem}, reflecting exclusive ownership.
Shared ownership would add unnecessary complexity, as the same physical \texttt{SubDetector} component would not normally be part of multiple \texttt{DetectorSystem} objects.
Copy constructors and assignment operators were deleted, to prevent copying of unique pointers. Duplicating a whole \texttt{DetectorSystem} would also not represent a meaningful physical operation.
Move construction and assignment were defaulted as \texttt{std::unique\_ptr} already provides safe ownership transfer.
\begin{lstlisting}[
    style=vscode, 
    caption={\texttt{DetectorSystem} member function interface to add \texttt{SubDetector} objects to the container.},
    label={lst:add_sub_detector}
    ]
    void add_sub_detector(std::unique_ptr<SubDetector> sub_detector);
\end{lstlisting}
\texttt{SubDetector} objects are added to the \texttt{DetectorSystem} using the member function stated in Code snippet \ref{lst:add_sub_detector}.
The full \texttt{DetectorSystem} configuration can be displayed using the member function \texttt{print\_configuration}, which iterates through the stored \texttt{SubDetector} objects in the same manner as \texttt{DetectorSystem::detect} in Code snippet \ref{lst:DetectorSystem_detect}.
As discussed in Section \ref{sec:min_func_SubDetectors}, \texttt{SubDetector::detect} is virtual, so each stored \texttt{SubDetector} can be called via the same interface, as seen in line 8.
\begin{lstlisting}[
    style=vscode, 
    caption={\texttt{DetectorSystem} member function implementation to pass the \texttt{Particle} through the all the owned \texttt{SubDetector} objects.},
    label={lst:DetectorSystem_detect}
    ]
void DetectorSystem::detect(Particle& particle) const
{
    std::cout << "--- Passing particle through DetectorSystem (" << sys_name << ") ---" << std::endl;
    std::cout << std::endl; // Line break.

    for (const auto& sub_detector : sub_detectors)
    {
        sub_detector->detect(particle);
    }

    std::cout << "-- Finished passing particle through DetectorSystem (" << sys_name << ") ---" << std::endl;
    std::cout << std::endl; // Line break.
}
\end{lstlisting}

\subsubsection{SubDetectors}
\label{sec:ad_feat_subdetectors}

The data member \texttt{status} goes beyond the minimum functionality, adding realism to the class. It makes physical sense to be able to switch a \texttt{SubDetector} on or off.
As will be seen in Section \ref{sec:ad_feat_detectorsystems}, a \texttt{SubDetector} contained within a \texttt{DetectorSystem} can also have its \texttt{status} modified by the said \texttt{DetectorSystem} container.

The \texttt{Particle} argument in  \texttt{SubDetector::detect} was not \texttt{const} to support the additional feature where \texttt{Calorimeter} objects stop the detected particles completely \cite{cms_detector}, hence altering the \texttt{Particle} object's \texttt{four\_momentum}.
This was implemented using the \texttt{Particle} base member function \texttt{absorb()} inside \texttt{Calorimeter::detect} function, as shown by Code snippets \ref{lst:ad_feat_absorb} and \ref{lst:ad_feat_calor_detect}.
A friend function approach, was considered as as I initially it thought it would allow a more physically aligned process to be programmed, with the \texttt{SubDetector} altering the \texttt{four\_momentum}.
However, this wasn't the case and hence granting the \texttt{SubDetector} access to the \texttt{Particle} protected data members produced no value.
Instead \texttt{Particle::absorb} was simpler and preserved encapsulation while still being applied within the \texttt{SubDetector::detect}.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{Particle::absorb} that alters the \texttt{Particle}'s \texttt{four\_momentum} returning its energy as its \texttt{rest\_mass} and hence that it is stationary.
    },
    label={lst:ad_feat_absorb}
    ]
void Particle::absorb()
{
    four_momentum->set_E(rest_mass);
    four_momentum->set_px(0.0);
    four_momentum->set_py(0.0);
    four_momentum->set_pz(0.0);
}
}
\end{lstlisting}
\begin{lstlisting}[
    style=vscode, 
    caption={
    Demonstration of how \texttt{Calorimeter} objects apply the \texttt{Particle::absorb} function to mimic the reality that the particles are completely stopped.
    },
    label={lst:ad_feat_calor_detect}
    ]
void Calorimeter::detect(Particle& particle) const
{
    // Check status of SubDetector.
    if (is_off())
    {
        return; // Exit function.
    }

    if (particle_interacts(particle)) // Removes code repetition by having detect differ in the derived classes.
    {
        std::cout << "Calorimeter (" << sd_name << ") measures the energy of the particle as: " << particle.get_four_momentum().get_E() << " MeV" << std::endl;
        // Will differentiate these later.
        std::cout << "The particle's true energy is: " << particle.get_four_momentum().get_E() << " MeV" << std::endl;
        std::cout << "The particle is absorbed." << std::endl;
        particle.absorb();
        std::cout << std::endl; // Line break.
    }
    else
    {
        std::cout << "Particle does not interact with the calorimeter (" << sd_name << "), no energy measurement." << std::endl;
        std::cout << std::endl; // Line break.
    }
}
}
\end{lstlisting}

\subsubsection{DetectorSystems}
\label{sec:ad_feat_detectorsystems}

Member functions for both removing and releasing \texttt{SubDetector} objects were added to the \texttt{DetectorSystem} container to add higher functionality. 
The \texttt{remove\_sub\_detector} function removes and destroys the owned \texttt{SubDetector}, as seen in Code snippet \ref{lst:remove_sub_detector}. This was physically motivated by the possibility of a detector component failing and needing to be removed or replaced.
\texttt{release\_sub\_detector} transfers ownership from the container to an external \texttt{std::unique\_ptr}. This allows the user to extract the \texttt{SubDetector} from the container while preserving the object itself, for example if the component is useful alone or in another \texttt{DetectorSystem}. It is applied in much the same way as Code snippet \ref{lst:remove_sub_detector}.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{DetectorSystem} member function to remove a \texttt{SubDetector} it owns. A lambda function is used in lines 7 to 10.
    },
    label={lst:remove_sub_detector}
    ]
void DetectorSystem::remove_sub_detector(const std::string& rem_sub_detector_name)
{
    // Find which index the SubDetector is at in the vector, if it exists.
    std::vector<std::unique_ptr<SubDetector>>::iterator it = std::find_if(
        sub_detectors.begin(),
        sub_detectors.end(),
        [&rem_sub_detector_name](const std::unique_ptr<SubDetector>& sub_detector)
        {
            return sub_detector->get_sd_name() == rem_sub_detector_name;
        }
    );

    if (it == sub_detectors.end())
    {
        std::cerr << "Error: SubDetector (" << rem_sub_detector_name << ") not found in DetectorSystem (" << sys_name << ")." << std::endl;
        std::cout << std::endl;
        return;
    }

    sub_detectors.erase(it);
    if (DSMessages::show_messages)
    {
        std::cout << "Removed SubDetector (" << rem_sub_detector_name << ") from DetectorSystem (" << sys_name << ")." << std::endl;
        std::cout << std::endl;
    }
}
\end{lstlisting}
Both member functions utilise a lambda function, an advanced C++ technique, when finding if the selected \texttt{SubDetector} is contained within the \texttt{DetectorSystem}.
This is carried out using the \texttt{algorithm} \texttt{std::find\_if} function which searches through the containing data member \texttt{sub\_detectors}.
A lambda function returns \texttt{true} if the \texttt{SubDetector} name of that iteration  matches the requested name.
\texttt{std::find\_if} then returns the iterator associated with the matching \texttt{SubDetector} or \texttt{sub\_detectors.end()} if no match is found.  
Its use here maintains clarity of the process because the search condition is defined directly where it is needed. Defining the same function elsewhere would achieve the same result but make this simple procedure less visible.
The lambda function therefore acts as a beneficial, small local attachment to \texttt{std::find\_if}, as seen in in lines 7 to 10 in Code snippet \ref{lst:remove_sub_detector}.
Note the member function \texttt{get\_sub\_detector}, mentioned below and in Code snippet \ref{lst:set_sub_detector_status}, uses the same \texttt{std::find\_if} and lambda function logic.

A wrapper member function \texttt{set\_sub\_detector\_status}, as seen in Code snippet \ref{lst:set_sub_detector_status}, was created to modify the \texttt{status} of a \texttt{SubDetector} contained in a \texttt{DetectorSystem}, increasing the functionality.
It does so by using \texttt{get\_sub\_detector} to return a non owning pointer to a contained \texttt{SubDetector}, if the requested name exists.
It is important that this pointer does not transfer ownership, so that the \texttt{DetectorSystem} object's \texttt{std::unique\_ptr} remains intact.
The returned pointer is only used to access and modify the contained \texttt{SubDetector}.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{DetectorSystem} member function to set a contained \texttt{SubDetector} object's \texttt{status}. It employs another member function \texttt{get\_sub\_detector} to return a non-owning pointer of \texttt{SubDetector}, as seen in line 3.
    },
    label={lst:set_sub_detector_status}
    ]
void DetectorSystem::set_sub_detector_status(const std::string& sub_detector_name, bool new_status)
{
    SubDetector* sub_detector = get_sub_detector(sub_detector_name);

    if (!sub_detector)
    {
        std::cerr << "Error: SubDetector (" << sub_detector_name << ") not found in DetectorSystem (" << sys_name << ")." << std::endl;    
        std::cout << std::endl;
        return;
    }
    
    sub_detector->set_status(new_status);
    if (DSMessages::show_messages)
    {
        std::cout << "Set SubDetector (" << sub_detector_name << ") status to -" << (new_status ? "on" : "off") 
        << "- in DetectorSystem (" << sys_name << ")." << std::endl;
        std::cout << std::endl;
    }
}

\section{Discussion and conclusions}

The main program successfully demonstrates an object oriented simulation of a particle detector.
The abstract base classes \texttt{Particle} and \texttt{SubDetector} provide a clear interface, allowing common properties to be inherited, and derived class specific properties to be implemented polymorphically.
This allowed \texttt{DetectorSystem} to store different derived \texttt{SubDetector} objects and pass different derived \texttt{Particle} objects through a detection function, meeting the minimum functionality.

The advanced features increased the physical realism and the usability of the program while applying advanced C++ techniques.
Further improvements would be to model the detectors as imperfect, including detector efficiency and fluctuations in measured energy.
The current \texttt{Particle} \texttt{four\_momentum} validation could also be improved, as only preventing negative energy does not stop unphysical \texttt{four\_momenta}, such as massive particles with $E^2 < p^2 +m^2$.
An interesting possibility would be to create a mechanism for particle interactions.
