\section{Design process \& considerations}

The design process is discussed in two stages: the implementation of the minimum functionality, followed by the reasoning behind the advanced features.
Both sections are structured around the main components of the program.
First, the development of the \texttt{Particle} class hierarchy is discussed, followed by the development of the \texttt{SubDetector} class hierarchy. Finally, the construction of the \texttt{DetectorSystem} class is described.

\subsection{Minimum functionality}

The minimum functionality of this project is paraphrased from the project slides below:
\begin{enumerate}
    \item Pure abstract base classes for a sub-detector and particle.
    
    \item Derived classes for sub-detectors: trackers, calorimeters and muon chambers.
    
    \item Derived classes for sub-detectors: electrons, muons, photons and hadrons.

    \item Virtual functions to set and get characteristics of the detectors and particles.

    \item Four-momentum is stored as a class in each particle.

    \item A detector that returns the energy of the particle it detected.

    \item A generic detector class that stores sub-detectors.    
\end{enumerate}
As we move through this section, the approach of how these were met is discussed.

The responsibilities previously held by Assignment 5's \texttt{Lepton} class were moved to this project's \texttt{Particle} base class, now extended to not just leptons.
To begin with, a simple \texttt{Electron} class was directly derived from \texttt{Particle}, without retaining the intermediate \texttt{ChargedLepton} layer used in Assignment 5. This simplified structure was chosen to test the initial interaction between the \texttt{Particle} and \texttt{SubDetector} classes before introducing a more complex class hierarchy.

The information regarding which \texttt{SubDetector} classes a derived \texttt{Particle} interacts with is stored in the \texttt{Particle} hierarchy rather than the \texttt{SubDetector} hierarchy.
This design choice was made for several considerations.
First, many interaction properties are shared by similar particles. Storing this information in the \texttt{Particle} hierarchy allows for common behaviour to be encoded through inheritance, reducing code repetition.
For example, \textcolor{red}{as shown in Code snippet \ref{lst:interacts_with_tracker}}, the data member \texttt{charge\_mag} determines whether a \texttt{Particle} interacts with a \texttt{Tracker}.
Since this logic/behaviour is the same for all particles, it can be defined once in the base class rather than repeatedly implemented in each derived class.

This design also supports future extension. If a new derived \texttt{Particle} is added, its interaction behaviour may already be defined and if not just needs introducing in that derived class implementation.
\textcolor{red}{An example of where a particle's behaviour is already defined is the case in which a new derived \texttt{Hadron} is created.}
In contrast, if the information was stored in the \texttt{SubDetector} hierarchy, each \texttt{SubDetector} derived class would have to be updated whenever a new \texttt{Particle} was introduced.
Note, it is also important to distinguish between whether a \texttt{Particle} can interact with a \texttt{SubDetector} and whether it is actually detected. The \texttt{interacts\_with} member functions define whether detection is physically possible for a given \texttt{Particle}.
\texttt{SubDetector} specific conditions, such as whether a \texttt{SubDetector} is switched on through its \texttt{status} data member, are still handled by the \texttt{SubDetector} classes.
This keeps the particle interaction logic separate from the detector measurement logic, improving both flexibility and clarity.

    }

\texttt{Particle} member functions, with the name beginning with \texttt{interacts\_with}, were chosen to handle \texttt{Particle}/\texttt{SubDetector} interaction instead of another idea, a \texttt{vector} data member that stores a list of \texttt{string} or \texttt{enum} data types.
This decision was first based on the fact that it allowed for simpler inheritance. Take for example the case of the \texttt{Hadron} class, like all \texttt{Particle} classes it inherited its \texttt{Tracker} behaviour from Code snippet \ref{lst:interacts_with_tracker}, and as its other behaviours were shared they were defined in \texttt{Hadron} and inherited by the derived and intermediate base classes below it.
This is simpler and clearer than defining a \texttt{vector} data member that is shared between derived classes.
Such a \texttt{vector} would store the result of the interaction logic, but would not express the logic itself as clearly as a dedicated member function as shown in Code snippet \ref{lst:interacts_with_tracker}.

The member function approach also improves adaptability, where the \texttt{vector} limits it. For example, if future development required \texttt{Muon} objects below a certain energy to not  interact with \texttt{MuonChamber} objects, this behaviour could be implemented naturally inside the relevant member function.
This design choice also makes \texttt{SubDetector} structure more straightforward. Each \texttt{SubDetector} only needs to call a single \texttt{bool} member function, rather than iterating through a \texttt{vector} to check whether the \texttt{Particle} interacts with it.

Upon reaching the minimum functionality for the \texttt{SubDetector} and \texttt{DetectorSystem} the class structures for \texttt{Muon}, \texttt{Photon} and \texttt{Hadron} were created, meeting item 3 of the minimum functionality.

As shown in Figure \ref{fig:Particle_UML}, the \texttt{Photon} class was derived directly from \texttt{Particle}.
This was because it has distinct physical properties and does not share sufficient common behaviour with the other particles required for minimum functionality, to justify an intermediate base class.
It became clear in \texttt{Photon} that the inherited data members \texttt{rest\_mass} and \texttt{is\_anti} were a bit redundant as it has no mass and is its own anti-particle.
However, they are not damaging and a necessity for the majority of the \texttt{Particle} classes. Therefore it was worthwhile and safe to keep them as base data members.
The base member function \texttt{print\_info}, which should print the characteristics common to all \texttt{Particle} objects did seem to be omitting information.
Rather than removing it, I added a statement to the \texttt{Photon} classes' polymorphic \texttt{Photon::print\_info} regarding the fact that \texttt{Photon} objects are their own anti-particles. 
The same was done for neutral the \texttt{Pion} \textcolor{red}{(and \texttt{Rho})}.

Since hadronic particles share similar properties and behaviour, they were organised under the intermediate base class \texttt{Hadron}. All interaction member functions were defined here and hence inherited by the derived classes, reducing repeated implementation.
A subsequent intermediate base class \texttt{Meson} was introduced, as they follow common charge dependent construction logic for the neutral and charged states.
This inheritance reduced repetition across the derived \texttt{Meson} classes and makes the hierarchy clearer, as shown in Figure \ref{fig:Particle_UML}.
The current choice not to group baryons under an additional intermediate base class like \texttt{Meson} was due to them not really sharing any behaviour that would make a move from \texttt{Hadron} valuable and worthwhile.
\textcolor{red}{They are so varied, with the example of sigma particles ($\Sigma^+,\Sigma^0, \Sigma^-$) more similar to the \texttt{Meson} structure, \texttt{Proton} structured more like a reverse \texttt{Electron} and Xi particles ($\Xi^0, \Xi^-$) following neither.}

The \texttt{SubDetector} hierarchy was first developed with the pure abstract base class and a single derived class, keeping the early structure simple so that the core interface could be tested before adding further complexity.
As can be seen in Figure \ref{fig:SubDetector_UML} the base data members are \texttt{sd\_name} and \texttt{status}.
\texttt{sd\_name} allows for \texttt{SubDetector} classes of the derived nature to be distinguished.
\texttt{status} allows for a \texttt{Detector} to be on or off \textcolor{red}{and will be expanded upon in the advanced features section as it is not required for the minimum functionality.}
Unlike \texttt{Particle}, \texttt{SubDetector} does not possess any dynamically stored data members. As seen in Figure \ref{fig:SubDetector_UML}, its data members are simple value types, so the default compiler copy/move constructors and assignment operators provide the correct behaviour. Therefore no custom copy/move semantics are implemented.
If such a data member was introduced, the method used in \texttt{Particle} could be adapted for \texttt{SubDetector}.

To meet the minimum functionality requirement of passing \texttt{Particle} objects through \texttt{SubDetectors}, a virtual base member function \texttt{detect} was developed. This function passes the \texttt{Particle} object as an argument, and as virtual, allows each derived \texttt{SubDetector} to define its own detection response.
This design provides a common interface for all \texttt{SubDetector} objects while preserving derived class specific implementation. This common interface is utilised in \texttt{DetectorSystem} to pass a \texttt{Particle} through all contained \texttt{SubDetector} objects efficiently, as discussed in Section \ref{sec:min_func_DetctorSystems} later. \textcolor{red}{And config.}

\subsubsection{DetectorSystems}
\label{sec:min_func_DetctorSystems}

\texttt{DetectorSystem} is a generic detector class that stores \texttt{SubDetector} objects, meeting the final minimum functionality item. The first data member is \texttt{string sys\_name} which allows for \texttt{DetectorSystem} objects to be differentiated. For example, if the user wanted to know whether it was the \textcolor{red}{CMS or ATLAS} \texttt{DetectorSystem} that returned the outputted measurements.
The second data member, as declared in Code snippet \ref{lst:container_pointer}, is a \texttt{vector} of unique pointers owning \texttt{SubDetector} objects.
This is what gives \texttt{DetectorSystem} its utility of being a container class.
\begin{lstlisting}[
    style=vscode, 
    caption={Data member for \texttt{DetectorSystem} to manage the ownership of multiple \texttt{SubDetector} classes.},
    label={lst:container_pointer}
    ]
    private:
    std::vector<std::unique_ptr<SubDetector>> sub_detectors;
\end{lstlisting}
I chose to use \texttt{std::unique\_ptr} rather than \texttt{std::shared\_ptr} to store the \texttt{SubDetector} objects, as it seemed unrealistic for the same detector component to be part of multiple major \texttt{DetectorSystem} objects.
Exclusive ownership also makes destroying \texttt{SubDetector} classes much easier, using shared ownership would therefore introduce unnecessary complexity without providing that much benefit.
Copy constructors and assignment operators were deleted to prevent the copying of unique pointers.
It is also non-physical that a whole \texttt{DetectorSystem} with its unique \texttt{SubDetector} objects would be copied exactly.
The move constructors and assignment operators \textcolor{red}{(check that they work)} are \texttt{defualt} as the compiler provides the correct handling of \texttt{std::unique\_ptr}.
\begin{lstlisting}[

    caption={\texttt{DetectorSystem} member function interface to add \texttt{SubDetector} objects to the container.},
    label={lst:add_sub_detector}
    ]
    void add_sub_detector(std::unique_ptr<SubDetector> sub_detector);
\end{lstlisting}
\texttt{SubDetector} objects can be added using the member function stated in Code snippet \ref{lst:add_sub_detector}, with the configuration printed via the member function \texttt{print\_configuration}, which uses a \texttt{for} loop similar to the one seen in Code snippet \ref{lst:DetectorSystem_detect}.
As mentioned earlier in Section \ref{sec:min_func_SubDetectors}, the fact that \texttt{SubDetector::detect} is virtual means that it can be called in the same way for all \texttt{SubDetector} objects, as seen in line 8.
\begin{lstlisting}[
    style=vscode, 
    caption={\texttt{DetectorSystem} member function implementation to pass the \texttt{Particle} through the all the owned \texttt{SubDetector} objects.},
    label={lst:DetectorSystem_detect}
    ]
    void DetectorSystem::detect(const Particle& particle) const
{
    std::cout << "--- Passing particle through DetectorSystem (" << sys_name << ") ---" << std::endl;
    std::cout << std::endl; // Line break.

    for (const auto& sub_detector : sub_detectors)
    {
        sub_detector->detect(particle);
    }

    std::cout << "-- Finished passing particle through DetectorSystem (" << sys_name << ") ---" << std::endl;
    std::cout << std::endl; // Line break.
}
\end{lstlisting}

\subsubsection{DetectorSystems}
\label{sec:ad_feat_detectorsystems}

Member functions for both removing and releasing \texttt{SubDetector} objects were added to the \texttt{DetectorSystem} container to add higher functionality. 
The \texttt{remove\_sub\_detector} function deletes a \texttt{SubDetector}, as seen in Code snippet \ref{lst:remove_sub_detector}. This was physically motivated by the possibility of a detector component failing and needing to be removed or replaced.
\texttt{release\_sub\_detector} transfers ownership from the container to an external \texttt{std::unique\_ptr}. This allows the user to extract the \texttt{SubDetector} from the container while preserving the object itself, for example if the component is useful alone or in another \texttt{DetectorSystem}. It is applied in much the same way as Code snippet \ref{lst:remove_sub_detector}.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{DetectorSystem} member function to remove a \texttt{SubDetector} it owns. A lambda function is used in lines 7 to 10.
    },
    label={lst:remove_sub_detector}
    ]
void DetectorSystem::remove_sub_detector(const std::string& rem_sub_detector_name)
{
    // Find which index the SubDetector is at in the vector, if it exists.
    std::vector<std::unique_ptr<SubDetector>>::iterator it = std::find_if(
        sub_detectors.begin(),
        sub_detectors.end(),
        [&rem_sub_detector_name](const std::unique_ptr<SubDetector>& sub_detector)
        {
            return sub_detector->get_sd_name() == rem_sub_detector_name;
        }
    );

    if (it == sub_detectors.end())
    {
        std::cerr << "Error: SubDetector (" << rem_sub_detector_name << ") not found in DetectorSystem (" << sys_name << ")." << std::endl;
        std::cout << std::endl;
        return;
    }

    sub_detectors.erase(it);
    if (DSMessages::show_messages)
    {
        std::cout << "Removed SubDetector (" << rem_sub_detector_name << ") from DetectorSystem (" << sys_name << ")." << std::endl;
        std::cout << std::endl;
    }
}
\end{lstlisting}
Both member functions utilise a lambda function, an advanced C++ technique, when finding if the selected \texttt{SubDetector} is contained within the \texttt{DetectorSystem}.
This is carried out using the \texttt{algorithm} \texttt{std::find\_if} function which searches through the containing data member \texttt{sub\_detectors}.
A lambda function returns \texttt{true} if the \texttt{SubDetector} name of that iteration  matches the requested name.
\texttt{std::find\_if} then returns the iterator associated with the matching \texttt{SubDetector} or \texttt{sub\_detectors.end()} if no match is found.  
Its use here maintains clarity of the process because the search condition is defined directly where it is needed. Defining the same function elsewhere would achieve the same result but make this simple procedure less visible.
The lambda function therefore acts as a beneficial, small local attachment to \texttt{std::find\_if}, as seen in in lines 7 to 10 in Code snippet \ref{lst:remove_sub_detector}.
Note the member function \texttt{get\_sub\_detector}, mentioned below and in Code snippet \ref{lst:set_sub_detector_status}, uses the same \texttt{std::find\_if} and lambda function logic.

A wrapper member function \textcolor{red}{\texttt{set\_sub\_detector\_status} maybe delete as word count}, as seen in Code snippet \ref{lst:set_sub_detector_status}, was created to modify the \texttt{status} of a \texttt{SubDetector} contained in a \texttt{DetectorSystem}, increasing the functionality.
It does so by using \texttt{get\_sub\_detector} to return a non owning pointer to a contained \texttt{SubDetector}, if the requested name exists.
It is important that this pointer does not transfer ownership, so that the \texttt{DetectorSystem} object's \texttt{std::unique\_ptr} remains intact.
The returned pointer is only used to access and modify the contained \texttt{SubDetector}.
\begin{lstlisting}[
    style=vscode, 
    caption={
    \texttt{DetectorSystem} member function to set a contained \texttt{SubDetector} object's \texttt{status}. It employs another member function \texttt{get\_sub\_detector} to return a non-owning pointer of \texttt{SubDetector}, as seen in line 3.
    },
    label={lst:set_sub_detector_status}
    ]
void DetectorSystem::set_sub_detector_status(const std::string& sub_detector_name, bool new_status)
{
    SubDetector* sub_detector = get_sub_detector(sub_detector_name);

    if (!sub_detector)
    {
        std::cerr << "Error: SubDetector (" << sub_detector_name << ") not found in DetectorSystem (" << sys_name << ")." << std::endl;    
        std::cout << std::endl;
        return;
    }
    
    sub_detector->set_status(new_status);
    if (DSMessages::show_messages)
    {
        std::cout << "Set SubDetector (" << sub_detector_name << ") status to -" << (new_status ? "on" : "off") 
        << "- in DetectorSystem (" << sys_name << ")." << std::endl;
        std::cout << std::endl;
    }
}
\end{lstlisting}
